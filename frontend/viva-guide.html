1 · The project

ShopKart is a two-tier application: a React single-page app on port 5173 and an Express + MongoDB API on port 3333. The frontend you are being examined on implements customer registration, login, session persistence, and route protection — nothing about carts or products yet. The "ShopKart" name is aspirational; the code is an authentication skeleton.

The single most important thing to understand before anything else: the frontend never sees the JWT. The token lives in an httpOnly cookie, so JavaScript cannot read it. That one decision explains almost every piece of the architecture — why there is a loading flag, why AuthContext calls /me on startup, and why the route guards have to wait.

2 · Concepts you must define

These are the definitions you should be able to give in one breath, without notes.

JSX — the question you will definitely be asked

Definition: JSX (JavaScript XML) is a syntax extension for JavaScript that lets you write HTML-like markup directly inside JavaScript code. It is not valid JavaScript and no browser can run it — it must be compiled first.

What actually happens to it: Vite's React plugin (via Babel/esbuild) rewrites every JSX expression into a function call that produces a plain JavaScript object — a React element. Modern React uses the automatic JSX runtime, so no React import is needed for the transform itself.

What you write
const el = <h1 className="title">Hello {name}</h1>;
What the compiler produces (roughly)
const el = jsx("h1", { className: "title", children: ["Hello ", name] });

// → a plain object, not a DOM node:
// { type: "h1", props: { className: "title", children: [...] } }

Why JSX instead of plain JavaScript? Four reasons, and this is the shape the answer should take:

  1. Readability. Building the same UI with React.createElement calls produces deeply nested function calls that are almost impossible to scan. JSX lets you see the structure of the page in the shape of the code.
  2. It is still JavaScript. You keep every language feature: embed expressions with {}, call .map(), use ternaries, variables, and functions. It is markup inside JS, not a separate template language like Angular's or Vue's.
  3. Early error detection. Unclosed tags, mismatched tags, and invalid nesting are caught at compile time with a line number — not silently at runtime in the browser.
  4. Safety. React escapes any value you interpolate with {}. So {userInput} can never inject markup — JSX is XSS-safe by default, unlike string-concatenating HTML or using innerHTML.

JSX rules you must be able to state

  • One root element. A component returns a single element. To return siblings, wrap them in a <div> or an empty fragment <>…</>.
  • className, not class. class is a reserved word in JavaScript, so JSX uses className. Similarly htmlFor instead of for.
  • camelCase attributes. onClick, onChange, tabIndex — not onclick.
  • {} holds an expression, not a statement. {2 + 2} works; {if (x) {}} does not — use a ternary or &&.
  • Tags must close. <input />, <br /> — self-closing is mandatory.

Core React concepts

Component

A reusable, self-contained function that returns JSX. It is the basic building block of a React UI — you compose a page out of components the way you compose a sentence out of words.

Components must be PascalCase (Login, Navbar). This is not style — it is how the JSX compiler tells your component <Login /> apart from a real HTML tag <div />. Lowercase names are always treated as HTML tags.

Props

Read-only inputs passed from a parent component to a child, written as attributes in JSX. They are immutable — a child must never modify its own props. This enforces one-way, top-down data flow, which is what makes React apps predictable.

In this project children is a prop: in <ProtectedRoute><Home /></ProtectedRoute>, the <Home /> element arrives inside the ProtectedRoute function as props.children.

State

Data owned and managed by a component that can change over time. When state changes, React re-renders that component and its children. State is local and private — unlike props, which come from outside.

State must be updated immutably: you never write credentials.email = x, you create a new object with the change. React compares references to decide whether to re-render, so mutating in place would be invisible to it.

Hook

A function whose name starts with use that lets a function component tap into React features it otherwise has no access to — state, lifecycle, context.

Two rules, non-negotiable: (1) only call hooks at the top level of a component — never inside loops, conditions, or nested functions; (2) only call them from React function components or from other custom hooks. React relies on call order to match hooks to their state, so a conditional hook would desynchronise everything after it.

useState

Declares a piece of state. Returns an array of two things: the current value and a setter function. const [user, setUser] = useState(null) — the argument is the initial value.

Calling the setter schedules a re-render. Updates are asynchronous and batched — the new value is not readable on the very next line, which is why you compute from the previous value rather than assuming it has changed.

useEffect

Runs side effects after render — things outside React's rendering job, like network requests, subscriptions, or manual DOM work.

useEffect(fn, deps). The dependency array controls when it re-runs: [] means run once after the first render (the mount); [x] means re-run whenever x changes; omitted entirely means run after every render. The function may return a cleanup function that runs before the next run or on unmount.

useContext

Reads the current value of a React Context from inside any descendant component, with no props passed through the middle. It subscribes the component to the context, so it re-renders whenever the context value changes.

Context API

React's built-in solution to prop drilling — the problem of passing a value through many intermediate components that do not themselves need it.

Three parts: createContext() creates the context object; <Context.Provider value={…}> makes a value available to everything nested inside it; useContext(Context) reads it.

It is used here for auth because five different components need the same user — Navbar, ProtectedRoute, PublicRoute, Home, and Login. Threading it through as props would mean passing it through components that have no interest in it.

Controlled component

A form element whose displayed value is driven by React state rather than by the DOM. You supply value={state} and onChange={handler}, so React becomes the single source of truth.

The alternative (uncontrolled) lets the DOM hold the value and you read it with a ref. Controlled is preferred here because it makes validation, resetting, and conditional enabling straightforward — every keystroke is already in state.

Virtual DOM

A lightweight in-memory JavaScript object tree that mirrors the real DOM. React renders to this tree first.

On a state change React builds a new tree, diffs it against the previous one (the process called reconciliation), and applies only the differences to the real DOM in a batch. Real DOM operations are expensive — this minimises how many happen.

Declarative UI

You describe what the UI should look like for a given state, and React works out how to get the DOM there. The mental model is UI = f(state).

The alternative — imperative — means manually calling document.createElement, appendChild, and removeChild and keeping the DOM in sync by hand. That becomes unmanageable quickly, which is the honest answer to "why React and not plain JavaScript?"

Synthetic event

React's cross-browser wrapper around the native browser event. Handlers like onClick and onSubmit receive a SyntheticEvent with a consistent API regardless of browser quirks.

e.preventDefault() on it cancels the browser's default action — used in this project to stop a form from doing a native submission and reloading the whole page.

Conditional rendering

Deciding what to render based on state, using ordinary JavaScript. Three forms appear in this codebase: the && operator ({user && <button />} — render only if truthy), the ternary (cond ? a : b), and an early return (if (!user) return null).

When the condition is false, && evaluates to false and React renders nothing for it.

Custom hook

A function starting with use that calls one or more built-in hooks and packages the result into reusable logic. useAuth is one: const useAuth = () => useContext(AuthContext).

Its value is encapsulation — components import useAuth rather than the raw context object, so the storage mechanism can change later without touching any consumer.

Platform concepts

SPA

Single Page Application. The server sends one HTML file; from then on all navigation happens in JavaScript without a full page reload. Only the parts of the DOM that changed are updated.

The benefit is speed and preserved state — a full reload would throw away all React state and re-download every asset.

React Router

The library that gives an SPA real URLs. BrowserRouter hooks into the browser's History API so the address bar updates and the back button works, even though no request is made to the server.

<Routes> looks through its <Route> children and renders the first one whose path matches the current URL. <Link> renders an anchor tag but intercepts the click and calls preventDefault internally, so the browser never navigates.

JWT

JSON Web Token — a signed, compact string encoding claims about a user (here, their id). The server signs it with a secret; anyone can read it, but nobody can forge or alter it without the secret.

It makes auth stateless: the server keeps no session table. It verifies the signature on each request and trusts the payload.

httpOnly cookie

A cookie with the httpOnly flag set is inaccessible to JavaScript — document.cookie cannot see it. The browser attaches it automatically to every matching request.

This is the standard mitigation for token theft via XSS: even if an attacker injects a script, it cannot read the token. The trade-off, and the thing to say out loud in a viva, is that the frontend therefore cannot know whether it is logged in without asking the server — which is exactly why AuthContext calls /me on mount.

CORS

Cross-Origin Resource Sharing. Browsers block JavaScript from reading responses from a different origin by default. The server opts in with an Access-Control-Allow-Origin header.

Because the frontend is localhost:5173 and the API is localhost:3333, these are different origins (an origin is scheme + host + port), so CORS applies. The backend allows exactly http://localhost:5173 with credentials: true — and that combination matters, because credentials: true is illegal alongside a wildcard * origin. The frontend must mirror it with withCredentials: true. Both sides are required; it is a two-way agreement.

Vite

A build tool and dev server. In development it serves your source files as native ES modules over HTTP — no bundling step — which is why startup is near-instant. Its HMR (Hot Module Replacement) and React Fast Refresh swap a changed module into the running page without losing state.

For production, vite build bundles and minifies everything with Rollup.

Tailwind CSS

A utility-first CSS framework. Instead of writing named classes in a stylesheet, you compose small single-purpose utilities directly in the markup: flex items-center px-6 py-4 bg-slate-900.

These are not CSS variables or shortcuts — each is a real class. Version 4 is CSS-first: @import "tailwindcss" in the entry stylesheet plus the Vite plugin, with no tailwind.config.js. It scans your source files and generates only the utilities actually used.

StrictMode

A development-only wrapper that deliberately double-invokes render functions and effects (mount → unmount → mount) to surface bugs from missing cleanup or impure code. It renders nothing visible and has no effect in production.

Practical consequence here: in dev you will see two GET /customers/me calls. That is expected, not a bug — and volunteering this is a strong answer if an examiner points at the network tab.

3 · File-by-file breakdown

What each file is, what it contains, and why it is written that way.

index.html

What it is: the only HTML file in the project. Every SPA has exactly one.

  • <div id="root"></div> is the mount point — the empty container React will take over. It ships empty; every pixel on screen is created by JavaScript.
  • <script type="module" src="/src/main.jsx"> loads the app. type="module" enables ES module syntax (import/export) in the browser.
  • <link rel="icon"> points at the favicon in public/, which Vite serves from the root URL.
Bug

Line 6 reads <meta fullName="viewport" content="width=device-width, initial-scale=1.0" />. It must be name="viewport". The attribute is currently meaningless, so the viewport meta tag is inert and the layout will not scale correctly on mobile. It looks like a casualty of a careless find-and-replace.

src/main.jsx

What it is: the JavaScript entry point — the first code that runs.

src/main.jsx
createRoot(document.getElementById('root')).render(
  <StrictMode>
    <App />
  </StrictMode>,
);
  • createRoot() is the React 19 API. It takes a DOM node and returns a root object. In React 17 and earlier this was ReactDOM.render() — mentioning the change is a good sign of depth.
  • .render(<App />) mounts the component tree into #root. React takes ownership of that node from here on.
  • import './index.css' pulls in the global stylesheet — this is what makes Tailwind available everywhere.
  • StrictMode wraps the app for development checks only.

src/App.jsx

What it is: the composition root. It does not hold any logic of its own — it wires the providers, the router, and the routes together. This is the file to open when asked "how does the app fit together?"

src/App.jsx (structure)
<AuthProvider>          ← auth state available to everything below
  <Router>              ← URL routing available to everything below
    <Navbar />          ← outside <Routes>, so it shows on every page
    <Routes>
      /register → <PublicRoute>   <Register /> </PublicRoute>
      /login    → <PublicRoute>   <Login    /> </PublicRoute>
      /home     → <ProtectedRoute><Home     /> </ProtectedRoute>
      *         → <Navigate to="/login" replace />
    </Routes>
  </Router>
</AuthProvider>

Four things worth being able to justify:

  • The nesting order is deliberate. AuthProvider is outside Router so that every route can read auth state. The guards are inside Router because <Navigate> needs router context to work at all. Inverting these would throw.
  • <Navbar /> sits outside <Routes>, so it renders on every page without repeating it in each route. It is still inside Router, which is what lets it use useNavigate.
  • path="*" is the catch-all — any unmatched URL. It redirects to /login, so a typo or a stale bookmark lands somewhere sensible instead of on a blank page.
  • replace on that Navigate replaces the current history entry rather than pushing a new one. Without it, hitting back would return you to the bad URL, which immediately redirects again — an inescapable back-button loop.

src/context/AuthContext.jsx

What it is: the most important file for the viva. It is the single source of truth for "who is logged in", and it owns the four operations the whole app depends on.

State it holds

  • user — the logged-in customer object, or null. Starts null.
  • loading — starts true. This is deliberate and load-bearing; see the callout below.

The session-restore effect

src/context/AuthContext.jsx
const fetchUser = async () => {
  try {
    const response = await api.get('/customers/me');
    setUser(response.data?.customer || response.data?.user || response.data);
  } catch (error) {
    setUser(null);
  } finally {
    setLoading(false);          // runs whether it succeeded or failed
  }
};

useEffect(() => {
  fetchUser();
}, []);                          // [] → run exactly once, after first render

This is the mechanism that keeps you logged in across a page refresh. Because the JWT is in an httpOnly cookie, JavaScript cannot check it — so the app asks the server. On a hard refresh, React state is wiped, user goes back to null, and this effect re-establishes the session from the cookie.

The line response.data?.customer || response.data?.user || response.data is defensive. The ? is optional chaining: if response.data is null or undefined, the whole expression short-circuits to undefined instead of throwing. The chain exists because the backend is inconsistent — /login returns { message, customer } while /me returns the raw user object. The fallbacks let one function handle both shapes.

The three operations it exposes

login(credentials)

POSTs to /customers/login, then immediately calls fetchUser(). The login response already contains the customer, but re-fetching from /me means there is exactly one code path that sets user — one source of truth. If the POST fails it throws, and the caller (Login.jsx) catches it.

logout()

POSTs to /customers/logout to have the server clear the cookie, and clears local state in a finally block — so the UI logs out even if the request fails. That finally is a deliberate robustness choice worth pointing out.

user, setUser, loading

Passed through the context value so consumers can read state directly. setUser is exposed but no component currently calls it — a small inconsistency you can acknowledge if asked.

The provider and the consumer hook
<AuthContext.Provider value={{ user, setUser, loading, login, logout }}>
  {children}
</AuthContext.Provider>

export const useAuth = () => useContext(AuthContext);

children here is the entire rest of the app — everything inside <AuthProvider> in App.jsx. The provider simply broadcasts the value down to all of it.

Key point

Why loading starts as true. On a refresh, there is a brief window where React has rendered but the /me request has not come back — so user is null even though the visitor has a perfectly valid cookie. If loading started as false, ProtectedRoute would see !user in that window and bounce a logged-in user to /login. The loading flag exists precisely to say "we don't know yet, don't decide." This is the single best answer you can give about this codebase.

src/components/ProtectedRoute.jsx

What it is: a guard component. It wraps a page and decides whether that page is allowed to render.

src/components/ProtectedRoute.jsx
const ProtectedRoute = ({ children }) => {
  const { user, loading } = useAuth();

  if (loading) return <div>Loading...</div>;
  if (!user) return <Navigate to="/login" replace />;

  return children;
};
  • { children } is destructuring props — it pulls children straight out of the props object.
  • The loading check comes first. Order matters: checking !user before loading is false would produce the redirect-flash bug described above.
  • <Navigate> is React Router's declarative redirect. Rendering it navigates immediately. It is a component, not a function call — that is why it lives in the JSX return rather than in the body.
  • replace prevents /home from being left in history, so the back button does not trap the user in a redirect loop.
  • return children — the guard itself renders nothing; it passes the wrapped page through unchanged.

This is the wrapper component pattern, sometimes called a layout route. It is preferred over duplicating the auth check inside every page because the rule lives in exactly one place.

src/components/PublicRoute.jsx

What it is: the inverse guard — for pages that only make sense when logged out.

src/components/PublicRoute.jsx
if (loading) return <div>Loading...</div>;
if (user) return <Navigate to="/home" replace />;

return children;

Same structure, opposite condition. It stops an already-logged-in user from landing on /login or /register — for example by pressing back after logging in, or typing the URL directly. They get sent to /home instead.

src/components/Navbar.jsx

What it is: the fixed header — the app title, and a Logout button that only appears when someone is logged in.

src/components/Navbar.jsx
const { user, logout } = useAuth();
const navigate = useNavigate();

const handleLogout = async () => {
  try {
    await logout();
    navigate('/login');
  } catch (err) {
    console.error('Logout error:', err);
  }
};

return (
  <nav className="flex justify-between items-center px-6 py-4
                  bg-slate-900 text-white shadow-md">
    <h1 className="text-xl font-bold tracking-tight">ShopKart</h1>
    {user && (
      <button onClick={handleLogout} className="bg-red-600 ...">Logout</button>
    )}
  </nav>
);
  • useNavigate() returns a function for programmatic navigation — moving the user in response to logic rather than a click on a link. <Link> cannot be used here because the navigation must happen only after the logout request resolves.
  • {user && (<button>…)} — conditional rendering. When user is null the expression is false and React renders nothing.
  • The logout sequence is ordered: clear the server session first, then navigate. Navigating first would briefly show /login while user is still set, which PublicRoute would immediately bounce back to /home.
  • The Tailwind classes: flex justify-between pushes the title and button to opposite ends; px-6 py-4 is horizontal and vertical padding; bg-slate-900 is the dark background.

src/pages/Login.jsx

What it is: the sign-in form. It demonstrates the controlled-component pattern end to end.

src/pages/Login.jsx — state and handler
const [credentials, setCredentials] = useState({ email: '', password: '' });
const [error, setError] = useState('');

const handleChange = (e) => {
  setCredentials({ ...credentials, [e.target.name]: e.target.value });
};

const handleSubmit = async (e) => {
  e.preventDefault();
  setError('');

  try {
    await login(credentials);
    navigate('/home');
  } catch (err) {
    setError('Invalid Credentials');
  }
};

There is real substance in handleChange, and it is a favourite exam question. It uses two ES6 features at once:

  • ...credentials — the spread operator. It copies every existing field into a new object. This is what makes the update immutable, which React requires.
  • [e.target.name] — a computed property name. The brackets mean "use the value of this expression as the key," not the literal string. Since each input has a name attribute matching a state field, one handler serves every input on the form.

Each input is wired as a controlled component: value={credentials.email} displays the state, and onChange={handleChange} writes back to it. State is the single source of truth, so clearing or validating the form is trivial.

e.preventDefault() is essential. Without it the browser performs its native form submission — a full page load to the same URL — which would destroy the entire React app and its state. It is the difference between a working SPA and one that reloads on every submit.

The error state drives a conditional banner: {error && <div className="…red…">{error}</div>}, and setError('') at the top of the handler clears any previous message before each attempt.

Finally, <Link to="/register"> at the bottom moves to the sign-up page without a reload, and Tailwind's hover:underline adds the underline on hover via a pseudo-class variant.

Weakness

The catch always reports "Invalid Credentials" — including for a 500 error, a network failure, or the server being down. Register.jsx does this better by reading err.response?.data?.message. Being able to point at that difference yourself is better than having it pointed out to you.

src/pages/Register.jsx

What it is: the sign-up form — structurally the same controlled pattern as Login, with four fields instead of two, plus two differences worth naming.

  • Client-side validation before the request. It checks all four fields are non-empty and sets an error immediately, saving a pointless round trip. Real validation still happens on the server — client validation is for user experience, never for security, because anyone can bypass it.
  • It calls api directly rather than going through context. Registration does not change global auth state, so there is no reason to route it through AuthContext. Matching the tool to the job is the right instinct.
src/pages/Register.jsx — submit and error handling
try {
  await api.post('/customers/register', formData);
  navigate('/login');
} catch (err) {
  setError(err.response?.data?.message || 'Registration failed. Try again.');
}

The error line is worth understanding in full. err.response?.data?.message uses optional chaining to safely reach the message, because a network failure has no response at all and would otherwise throw a second error inside the catch block. The || supplies a fallback for that case. This surfaces the backend's real message — "Email must be unique" or "Password too short" — instead of a generic one.

On success it navigates to /login rather than straight to /home. That is a deliberate product decision: the user proves the credentials they just chose actually work, rather than being silently logged in. Either choice is defensible — just have a reason.

Detail

The field is named fullName, not name, in both the state object and the name attribute. This is not arbitrary — it matches the backend's req.body destructuring exactly. Renaming it in the frontend would silently break registration.

src/pages/Home.jsx

What it is: the protected page — a read-only profile view, and the proof that the whole auth chain works.

src/pages/Home.jsx
const { user } = useAuth();

if (!user) return null;

return (
  <div>
    <h2>Welcome back, {user.name}!</h2>
    <p>Full Name: {user.name}</p>
    <p>Email: {user.email}</p>
    <p>Phone: {user.phone}</p>
  </div>
);

{user.name} is JSX interpolation — a JavaScript expression inside braces, evaluated and rendered as text.

Bug

user.name does not exist. The Mongoose schema defines the field as fullName, so user.name is undefined. The page currently renders "Welcome back, !" and a blank Full Name row, while Email and Phone work correctly. The fix is user.fullName on both lines. Know this one — it is exactly the kind of thing an examiner spots on screen and asks you to explain. Owning it and describing the fix is a much better look than being caught by it.

The if (!user) return null guard is technically redundant — ProtectedRoute already guarantees a user. It is harmless defensive coding, and the honest answer is that it protects against the brief moment during navigation when context may not yet be populated. On its own, the early return null pattern is a clean way to skip rendering when preconditions are not met.

src/axiosCalls/axios.js

What it is: four lines, and one of the most consequential files in the project.

src/axiosCalls/axios.js
const api = axios.create({
  baseURL: "http://localhost:3333",
  withCredentials: true,
});
  • axios.create() builds a preconfigured instance. Every call made through api inherits these settings. The alternative — repeating the full URL and options on every request — is error-prone and painful to change. If the backend moved, this is the one line you would edit.
  • baseURL is why the rest of the app writes api.get('/customers/me') instead of the full address.
  • withCredentials: true is essential and easy to miss. By default, browsers do not send or store cookies on cross-origin requests. Without this flag the httpOnly token cookie is never attached, so every request to /me returns 401 and the user appears permanently logged out — even though login itself "succeeded". It must be paired with credentials: true in the backend's CORS config. A mismatch on either side produces exactly the same silent failure.

vite.config.js

Two plugins. react() compiles JSX and provides Fast Refresh. tailwindcss() is the Tailwind v4 Vite integration — it scans source files for class names and generates the matching CSS. There is no tailwind.config.js in this project, which is the v4 difference: configuration is done in CSS now.

One line. This import is what injects Tailwind's base styles and all generated utilities into the app. It is imported once, in main.jsx.

4 · End-to-end workflows

The four sequences you should be able to narrate from memory, in order. If you can walk an examiner through these, you have passed.

Flow A — App boot and session restore

This is the one that runs on every refresh, and the one that reveals whether you understand the architecture.

  1. The browser loads index.html. <div id="root"> is empty — the page is blank white.

  2. main.jsx executes. createRoot() targets #root and .render() mounts the tree.

  3. AuthProvider initialises: user = null, loading = true.

  4. Router, Navbar, and Routes render. First paint happens here — the Loading state.

  5. After that first render, the useEffect fires and calls fetchUser(), which sends GET /customers/me.

  6. The browser automatically attaches the httpOnly token cookie — JavaScript never touches it.

  7. On the server, isAuthenticated reads req.cookies.token, verifies the JWT signature with the secret, looks the user up by the id in the payload, attaches it as req.user, and calls next().

  8. The controller responds with the user object. setUser(data) stores it; the finally block sets loading = false.

  9. React re-renders. The guards now have their answer.

  10. On /home: loading is false and user exists, so ProtectedRoute renders Home. If the cookie was missing or expired the server returned 401, user stays null, and <Navigate to="/login"> takes over.

The point

Step 4 renders before step 8 can possibly finish. That gap is the entire reason loading exists. Explain that gap and you have explained the design.

Flow B — Register a new account

  1. The user types into any of the four inputs. Each keystroke fires onChange → handleChange → setFormData with a spread copy and a computed key → re-render with the new value shown. The DOM is never the source of truth.

  2. The user submits. React calls handleSubmit, and e.preventDefault() cancels the browser's native form submission — no page reload.

  3. Client-side check: any empty field sets an error message and returns early. No request is sent.

  4. api.post('/customers/register', formData) sends the JSON body.

  5. Backend: validates all fields are present; queries for an existing email and returns 409 if found; checks the password is at least 6 characters; hashes it with bcrypt at cost factor 10; creates the user; strips the password from the response.

  6. On 200, navigate('/login') moves to the sign-in page.

  7. On error, err.response?.data?.message is displayed — the server's own wording, with a generic fallback for network failures.

Flow C — Login

  1. Controlled inputs capture email and password into credentials state.

  2. handleSubmit clears any old error, calls e.preventDefault(), then await login(credentials) — the context function, not axios directly.

  3. AuthContext.login POSTs to /customers/login.

  4. Backend: finds the user by email (401 if absent), compares the password with bcrypt.compareSync (401 if wrong), signs a JWT containing the user id, and sets it as an httpOnly cookie on the response.

  5. The browser stores the cookie — this only happens because withCredentials: true is set on the axios instance and the backend's CORS allows credentials from this origin. Both must line up.

  6. login() then awaits fetchUser(), which calls /me — now succeeding, since the cookie is in place — and sets user.

  7. navigate('/home') runs only after both awaits resolve.

  8. Routes matches /home; ProtectedRoute sees a user and renders Home. Meanwhile Navbar re-renders and the Logout button appears.

  9. If any step threw, the catch sets "Invalid Credentials" and the user stays on the form.

Flow D — Logout

  1. The user clicks Logout in Navbar, firing handleLogout.

  2. await logout() → POST /customers/logout, with the cookie attached. The route is behind isAuthenticated, so the token is verified first.

  3. The backend responds with res.clearCookie('token'), instructing the browser to drop it.

  4. The finally block sets user = null regardless of whether the request succeeded — local state and server state are cleared independently.

  5. navigate('/login') runs. PublicRoute sees no user and renders the login page. Navbar's {user && …} now evaluates false and the button disappears.

The API contract

Frontend callBackend routeAuth?Response
api.post('/customers/register')POST /customers/registerNo200 { success, message, customer } · 400 · 409
api.post('/customers/login')POST /customers/loginNo200 { message, customer } + sets cookie · 401
api.get('/customers/me')GET /customers/meYes200 raw user object · 401

Note the inconsistency the frontend has to absorb: /login wraps the user in a customer key, but /me returns the bare object. That is why AuthContext has its three-way fallback chain rather than a single direct assignment.

5 · Weak points & bugs

Know these before the examiner finds them. Voluntarily naming a flaw and its fix reads as understanding; being caught by one does not.

Real bug · high priority

user.name is always undefined. Home.jsx lines 11 and 13 read user.name, but the backend schema field is fullName. The welcome heading renders "Welcome back, !" with the name missing. Fix: user.fullName. This is visible on screen, so it is the most likely thing to be spotted.

Real bug

fullName="viewport" in index.html. Should be name="viewport". The meta tag is inert, so responsive breakpoints will not behave correctly on an actual phone. Another artifact of a global find-and-replace that was not scoped to the right file.

Error swallowing

AuthContext.fetchUser catches every error and calls setUser(null). A network failure or a server that is simply down is therefore indistinguishable from "not logged in" — the user gets bounced to the login page rather than being told something is broken. Distinguishing err.response?.status === 401 from the absence of a response would fix it.

Generic login error

Login.jsx hardcodes "Invalid Credentials" in its catch, so a 500 or a dead server reports the same thing as a wrong password. Register.jsx already does this correctly — the two files are simply inconsistent.

Logout needs auth

POST /customers/logout sits behind isAuthenticated. If the cookie has already expired, logout returns 401. The frontend survives this because finally clears local state anyway — but the catch will log an error in the console that looks alarming and is not.

Cookie flags

The backend sets { httpOnly: true } only — no sameSite, no secure. This works on localhost because ports are not part of "same site", so 5173 → 3333 is same-site and the default SameSite=Lax permits it. In production, where the frontend and API are usually on genuinely different domains, you would need sameSite: 'none' together with secure: true and HTTPS. Knowing this is a strong answer.

No token expiry handling

There is no refresh flow and no explicit expiry handling. When the JWT expires, /me returns 401 and the app simply treats the user as logged out. Acceptable for a lab project; worth naming as a limitation rather than being surprised by it.

setUser exposed but unused

setUser is passed through the context value but no consumer calls it. Minor, but it is the kind of loose end that invites "why is this here?"

Loading state duplication

Both guards render the literal string "Loading..." with no styling, and there is no loading indicator anywhere else. Purely cosmetic, but a spinner or skeleton would be the production answer.

6 · Rapid-fire questions

Click a question to reveal the answer. Try answering aloud first.

What is JSX and why use it instead of plain JavaScript?

JSX is a syntax extension that lets you write HTML-like markup inside JavaScript. It is not valid JS — the build tool compiles it into jsx() calls that produce plain objects called React elements. We use it over raw React.createElement because it is far more readable, it keeps the full power of JavaScript (expressions, map, ternaries) rather than being a limited template language, it catches malformed markup at compile time, and React escapes interpolated values so it is XSS-safe by default.

Why className and not class?

Because JSX is JavaScript, and class is a reserved keyword in JavaScript (used for class declarations). Using it as an attribute name would be a syntax error, so React uses className. The same logic explains htmlFor instead of for.

What is the virtual DOM and why does React use it?

An in-memory JavaScript object tree mirroring the real DOM. When state changes React builds a new tree, diffs it against the previous one (reconciliation), and applies only the differences to the real DOM. Real DOM operations are expensive, so this minimises how many happen and batches them.

Difference between props and state?

Props are passed in from a parent and are read-only — a component must never modify its own props. State is owned and managed inside the component, and changing it triggers a re-render. Props flow one way, top-down; state is private to the component that declares it.

What does the [] in useEffect(fn, []) mean?

An empty dependency array means the effect runs exactly once, after the first render (on mount), and never again. Adding a value to the array makes it re-run whenever that value changes. Omitting the array entirely makes it run after every render. Here it fetches the user once on startup.

Why is there a loading flag at all?

Because the JWT is in an httpOnly cookie that JavaScript cannot read, the app cannot know whether it is logged in until /me responds. On a refresh there is a window where user is still null despite a valid session. Without loading, ProtectedRoute would redirect a logged-in user to /login during that window. loading starting as true means "we don't know yet — don't decide."

Why is the token stored in an httpOnly cookie rather than localStorage?

Any script running on the page can read localStorage, so an XSS attack can steal the token outright. An httpOnly cookie is invisible to JavaScript — the browser attaches it automatically — so injected scripts cannot exfiltrate it. The trade-off is that the frontend cannot inspect it, which is why the app must call /me to learn its own auth state.

What does withCredentials: true do?

It tells the browser to send and store cookies on cross-origin requests, which it refuses to do by default. Without it, the httpOnly token cookie is never attached to requests to the API, so /me always returns 401 and the user appears logged out even though login returned 200. It must be matched by credentials: true in the backend's CORS config — both sides are required.

Why call e.preventDefault() in the submit handler?

By default a form submission performs a native browser navigation — a full page load. In an SPA that would destroy the entire React tree and all its state. preventDefault() cancels the browser's default action so the JavaScript handler can take over entirely.

Explain { ...credentials, [e.target.name]: e.target.value }.

The spread operator copies every existing field into a new object, which keeps the update immutable — React compares references, so mutating in place would not trigger a re-render. The bracketed key is a computed property name: it uses the value of e.target.name as the key rather than the literal string. Because each input's name attribute matches a state field, one handler serves the whole form.

Why does AuthProvider wrap Router and not the other way round?

Every route needs to read auth state, so the provider has to be an ancestor of all of them. The guards use <Navigate>, which requires router context, so they must be inside Router. Putting the provider outside the router satisfies both — and inverting the order would break useAuth in ProtectedRoute.

Why replace on the <Navigate> components?

It replaces the current history entry instead of pushing a new one. Without it, an unauthorised visit to /home would push /login on top of /home; pressing back would return to /home, which would immediately redirect to /login again — the user could never leave. replace keeps the history clean.

What is a controlled component? Give an example from this code.

A form element whose value is driven by React state via value and onChange, making React the single source of truth rather than the DOM. Every input in Login.jsx and Register.jsx is controlled — value={credentials.email} with onChange={handleChange}.

Why does the network tab show two /me requests in development?

StrictMode deliberately mounts, unmounts, and remounts components in development to expose missing cleanup functions and impure code. The effect runs twice as a result. It has no effect in the production build — it is not a bug.

Why is Navbar outside <Routes>?

So it renders once and persists across every route, instead of being repeated inside each route's element. It is still inside Router, which is what allows useNavigate to work — but being outside Routes means it must tolerate user being null on its own, which it does with {user && …}.

Why does Register.jsx navigate to /login instead of /home?

So the user explicitly proves the credentials they just created actually work. It is a product decision, not a technical constraint — auto-login after registration would also be valid, and the backend already returns the created customer either way.

What does err.response?.data?.message do, and why the question marks?

Optional chaining: if any link in the chain is null or undefined, the whole expression short-circuits to undefined instead of throwing a TypeError. It matters here because a network failure produces an error with no response property at all — accessing err.response.data directly would throw a second error inside the catch block. The || then supplies a fallback message.

Why is Tailwind used instead of plain CSS files?

It removes the naming problem (no inventing class names), keeps styles colocated with the markup they apply to, and ships only the utilities actually used, so the CSS never grows unbounded. The cost is verbose markup, which is the standard trade-off. In v4 there is no config file — @import "tailwindcss" plus the Vite plugin is the whole setup.

Is client-side validation in Register.jsx enough?

No. It exists purely for user experience — to avoid a pointless round trip. Anyone can bypass it with dev tools or by calling the API directly, so the backend repeats every validation (required fields, unique email, minimum password length). Client-side validation is never a security control.

Where would you add a new protected page, and what would you change?

Create the component in src/pages/, then add a <Route> in App.jsx with its element wrapped in <ProtectedRoute>. Nothing else changes — the guard, the context, and the axios instance are all already in place. That the change is one file is the payoff of the wrapper pattern.
